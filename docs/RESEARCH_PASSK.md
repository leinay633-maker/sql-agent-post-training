# pass@k 预注册：RL 是不是只在挑答案（能力边界）

写于 2026-10-29（北京时间），在任何 pass@k 运行之前。协议 `efa-passk-v1`。不训练，只采样。

## 为什么做

- v0.11 的主比较 RLb−PTR 成立（贪心，项目判分）：test +2.6 [+0.7, +4.7]。v0.12 的 OPD−B 成立：test +4.7 [+1.1, +8.3]。
- 这些都是 pass@1。NeurIPS 2025 的口头报告论文（arXiv 2504.13837）在数学和代码上发现：
  - 可验证奖励的 RL 让小 k 的 pass@k 变高；
  - 到大 k，原模型追上甚至反超；
  - 作者的解释是，RL 只是把原模型本来就能采到的答案排到前面，没有扩大能采到的范围（能力边界）。
- 本研究在多步、带执行反馈的 SQL Agent 上问同一个问题，用手上已经训好的模型，不再训练。

问题：

1. **主问题**：RL 这一步（RLb，对它的起点 PTR）k=1 时更高，k=64 时还更高吗？
2. **次问题**：离线蒸馏加 DPO（PTR−B）、在线蒸馏（OPD−B）、整条流水线（RLb−B）在大 k 时怎样。
3. 探索：OPD−PTR。

## 固定内容

- 题目：v0.5 注册的 test 1501 题，来自 BIRD dev 的 11 个数据库。冻结时核对注册的四个文件，只保留 test。
- Agent 协议、判分：与 v0.5–v0.12 相同。
  - 最多 4 步，含一次结果复核；上下文 8192，单步 512 token；
  - SQL 限制 10 亿 VM 步、墙钟 30 秒、1 万行、8 MB；
  - 项目判分，对照冻结时执行的金标缓存；金标不进入模型输入；
  - 上下文超长被拒的对话按错计，与训练一致。
- 模型，共 10 个，学生都是 `Qwen/Qwen3-4B-Instruct-2507` @ `cdbee75f`：
  - B：原版，不挂 LoRA；
  - PTR_seed42/43/44：v0.8 正式 run `b51e3635…`，离线蒸馏加 DPO，是 RLb 的起点；
  - RLb_seed42/43/44：v0.11 正式 run `7b9bca19…`，在它登记的比较点 K=200；
  - OPD_seed42/43/44：v0.12 正式 run `8834421c…`，在它登记的比较点 K=260。
- 冻结时的核对：
  - v0.8、v0.11、v0.12 各自的 manifest 身份、题目注册和 4B 快照；
  - 两个 run 的里程碑记录与 adapter 哈希；
  - 每个 seed 的 RLb 必须正好在第 200 步、OPD 正好在第 260 步，没训满、用最后一步顶替的里程碑不收；
  - v0.11 的 RLb 每个 seed 的起点就是这里导入的同 seed PTR。
- 采样：
  - 每个模型每题 64 段对话；
  - 温度 1.0、top_p 1（不截断），与 v0.9–v0.12 在线训练时一样，冻结时与 v0.11、v0.12 的设置逐项核对；
  - vLLM 0.11.2；每个采样器占半张卡，KV 缓存固定 28 GiB；一张卡同时跑两个；
  - 每个模型的题序按 `sha256(salt:passk:模型:题号)` 排，32 题一块落盘，中断后从下一块接着采。

## 指标

- 每题的 pass@k 用无偏估计 1 − C(n−c, k) / C(n, k)：n = 64，c 是做对的条数，k = 1、2、4、8、16、32、64。
  - 一个模型的 pass@k 是 1501 题的均值；
  - 一个家族的 pass@k 是 3 个 seed 的均值。
- 差值区间用数据库×seed 聚类 bootstrap，2000 次，与 v0.6 起各版的方案相同：
  - 每次有放回地抽 11 个数据库，每题按所在数据库被抽中的次数加权；
  - 同时有放回地抽模型对；
  - 95% 区间取 2.5% 和 97.5% 分位；所有 k 和所有比较用同一组抽样。
- 配对：PTR、RLb、OPD 之间按 seed 配对；与 B 比时，B 对每个 seed 广播。

## 比较与判定

| 比较（后者 − 前者） | 性质 |
|---|---|
| RLb−PTR（RL 这一步） | 主 |
| PTR−B（离线蒸馏加 DPO） | 次 |
| OPD−B（在线蒸馏） | 次 |
| RLb−B（整条流水线） | 次 |
| OPD−PTR | 探索 |

- 每个比较在 k=1 和 k=64 各判一次：下界 > 0 判"更高"，上界 < 0 判"更低"，否则判"分不开"。
- **"RL 这一步收窄了能力边界"**：RLb−PTR 在 k=1 更高，且在 k=64 更低。
- 其他组合按字面写。例如 k=1 更高、k=64 分不开，写成"k=64 未检出差异，无法判断是否追平，既不能说收窄，也不能说扩大"。
- 交叉点：在 1 到 64 的每个整数 k 上算差值的点估计，取第一次 ≤ 0 的 k，只作描述。
- 没采完的模型不参与比较，报告里点名；缺 seed 的比较照算，标"缺 seed"。

## 事先估计（只写定性）

- PTR−B 在各 k 都为正。
- RLb−PTR 在 k=1 为正，随 k 增大而变小；到 k=64 会不会变负，是本研究要回答的。
- OPD 不做预期。

## 排除"蒙对"的影响

- 背景：test 金标里 902 题的结果只有一个格子（一个数或一个名字），599 题至少两个格子。采 64 次时，写错的 SQL 碰巧算出同一个值也会被判对。k 越大，这种情况越多，而且更抬高原本做不对的模型。
- **分层**：每个比较在两层上分别报，bootstrap 方案相同，只用该层的题。
  - k=64 判了"更高"或"更低"时，多格子题上的点估计同号才算稳健；
  - 不同号，写明"可能受单值答案影响"。
- **抽查**，结果拉回本机后做：
  - 对象：RLb−PTR 和 RLb−B 两个比较中"只有一方做对"的题。一方的全部对话里至少对一条，另一方一条都没对。两个方向分开。
  - 对话数：B 每题 64 条，其他家族 3 个 seed 共 192 条。两方不对等，所以抽查只看每个方向里蒙对的比例，不用来比哪方更强。
  - 抽样：每个方向用固定 seed 抽最多 30 题，取这一方第一条做对的最终 SQL。
  - 标注：对照问题、提示和金标 SQL，标为"逻辑正确 / 碰巧对上 / 说不清"。
  - 由本机 Claude Code 先标一遍，再交一个不同模型的独立子代理，在看不到第一遍的情况下再标一遍。
  - 报告每个方向蒙对的比例和两遍的一致率。

## 解码对照（运行前加入）

- 背景：B 和 PTR 没在自己温度 1 的采样上训过，RLb 和 OPD 是边采边训出来的。温度 1 且不截断时，B 和 PTR 可能更常采到低概率的怪词，把 SQL 或格式弄坏，在大 k 下也显得追不上。这个偏差与"蒙对"方向相反。
- 做法：
  - 模型：seed 42 的 PTR 和 RLb。
  - 题目：按 `sha256(salt:control:题号)` 取 test 中固定的 500 题。
  - 解码：模型卡推荐的设置，温度 0.7、top_p 0.8、top_k 20。
  - 采样：每题再各采 64 次。
- 报告：在同一批 500 题上，比较两种解码下 RLb−PTR 各 k 的差值和区间。只有 1 个 seed，只重抽数据库。
- 判读，看 k=64 的点估计在两种解码下的乘积：
  - 大于 0（同号）：主结论照写；
  - 小于 0（异号）：主结论写明"依赖解码设置"；
  - 等于 0（至少一种解码下差值恰为 0）：不判，报告写明哪种解码为 0。
  - 这个对照同时改了温度和截断，只用来检查稳健性，不估计温度单独的作用。

## 描述性（不判定）

- 多样性：每题 64 条里不同最终 SQL 的条数，比较前统一空白和大小写；没有最终 SQL 的对话占比。
- 温度 1 的 pass@1 对比各模型在自己 run 里的贪心分数（不是同一晚测的）。
- 吞吐、耗时、上下文超长被拒和到达 512 token 上限的次数。

## 上机：单张 H20，预约 36 小时

- 环境与冻结约 50 分钟。
- 冒烟约 25 分钟：16 题，每题 16 条，覆盖 seed 42 的 4 个模型和解码对照，最后出报告。两个采样器同时加载在一张卡上，各自以满并发（256 段对话）跑一块；第二个晚 150 秒启动，两者的生成不一定重叠。冒烟全部采完、报告写出后，正式采样才开始。
- 正式采样：12 个作业，每个占半张卡，同时跑两个。
  - 顺序：seed 42 的 PTR、RLb、B、OPD → 解码对照 → seed 43 的 PTR、RLb → seed 44 的 PTR、RLb → seed 43、44 的 OPD。
  - 估时按半张卡上每题（64 条）14 秒：整题集作业每个约 5.8 小时，对照作业每个约 1.9 小时；两个并行，纯采样约 31 小时，加上每个作业约 10 分钟的加载，约 32 小时。每题 12.4 秒时约 28.5 小时，16 秒时约 36.6 小时。
- 主比较成对放行：同一 seed 的 PTR 只在估计它的 RLb 也能在截止前采完时才启动，RLb 等它的 PTR 启动后才启动，避免只采了一半的模型对。
- 预约不够时，调度器按本机实测速度估时，排不进的作业不启动，按上面的顺序从后往前舍弃：先是 seed 43、44 的 OPD，最后才是 seed 44 的 PTR、RLb 这一对。按 36 小时预约粗算：
  - 每题 14 秒左右，12 个作业都能采完；
  - 15 秒左右，舍弃 seed 43、44 的 OPD；
  - 慢到 20 秒左右，也保得住 seed 42 的全部模型、解码对照和 seed 43 的主比较。

## 上机修订：拆到两台单卡（运行前，2026-10-30）

- 起因：约不到一整段 36 小时的单卡。改为同时开两台单卡 H20，分别约 21 小时和 24 小时，共 45 卡时。两台用同一个上传包和同一份设置，各采一部分模型（`passk_run.sh --only`）：
  - 21 小时那台：seed 42 的 PTR、RLb、B、OPD，解码对照，seed 43、44 的 OPD；
  - 24 小时那台：seed 43、44 的 PTR、RLb 两对，采样留约 13.5 小时，其余时间跑部署研究。
- 每台各自冻结、冒烟，按本机实测速度决定作业是否启动；成对放行和舍弃顺序与上一节相同，只是在各自的模型范围内。
- 合并：冻结记录里的金标缓存带每条参考 SQL 的执行耗时，所以两台的 run 编号不同。拉回后在本机核对，两边除执行耗时外的冻结内容完全一致：设置、导入及其哈希、题目、金标结果、代码。核对通过，才把第二台的采样记到第一台的 run 下，并保留原编号和核对记录。两台各自出的报告只是中间结果；按本文判定的是合并后 run 的报告，判定标准、模型、采样设置都不变。两台都装在 `/root/efa-passk/` 下，冻结记录里的数据和模型路径才一致。核对不通过时，两台的结果分开报告，不合并比较。
- 估时（每题 14 秒）：24 小时那台的两对分两轮，约 12 小时，留有余量，所以主比较的三个 seed 都排得进。21 小时那台约有 19 小时采样窗口，采完 seed 42 的四个模型和对照后，每题约 13 秒以内才排得进 seed 43、44 的 OPD。

## 不声称的内容

- 单一数据集（BIRD dev）、单一 4B 模型、LoRA，结论只适用于本协议。
- pass@k 是"采 k 次至少一次做对"的概率，不是部署时能拿到的准确率，因为部署时不知道哪一条是对的。
- RLb 和 OPD 只在各自登记的步数上比较，不推广到其他步数。
- 解码对照只有 seed 42 和 500 题，只用来判断结论是否依赖解码。
- 执行结果一致只说明在固定的数据库快照上结果相同，不等于语义等价；抽查的标注是人工判断。
