# v0.11 预注册：只在起点的边界题上做在线 RL（执行结果作奖励）

写于 2026-10-21（北京时间），在任何 v0.11 运行之前。协议 `efa-v11-boundary-rl-v1`。

## 为什么有 v0.11

- v0.9 的主比较 RL−PTR（项目判分）没有成立：test +1.4 [−0.1, +2.8]，validation +1.9 [+0.2, +3.3]，test 下界差 0.1。RL 在 test 上官方 EX 55.6–57.8%（均值 56.9%），同晚重评的 PTR 均值 55.4%。
- v0.9 每步 16 题 × 8 条对话里，有训练信号的组只占 13–20%。组内 8 条全对或全错时 RLOO 的优势为 0，这些采样不产生梯度。
- v0.9 的 RLhi（lr 5e-5，2 个 seed）test +2.6 [+0.4, +6.0]，但 validation 并不比 RL 好（RLhi−RL validation −0.8）。它是探索性结果，本版不以它为依据。
- v0.10 的全参 RL 比 LoRA RL 低（test −4.2 [−7.1, −1.2]），而且要多卡。本版不涉及全参。

问题：

1. **主问题**：只在每个起点的边界题上训练，其余与 v0.9 的 RL 完全相同，在线 RL 能否超过 PTR（RLb vs PTR）。
2. **次问题**：同样 200 步、同样学习率，只训边界题本身是否带来提升（RLb vs v0.9 的 RL，本版记作 RL9）。

## 固定内容

- 题目、Agent 协议、判分：与 v0.9 完全相同。
  - v0.5 注册：pool 6682 / dev 615 / validation 1612 / test 1501；
  - 最多 4 步，含一次结果复核；上下文 8192，单步 512 token；
  - SQL 限制 10 亿 VM 步、墙钟 30 秒、1 万行、8 MB。
- 学生：`Qwen/Qwen3-4B-Instruct-2507` @ `cdbee75f`。
- 起点：v0.8 正式 run `b51e3635…` 的 PTR_seed42/43/44。冻结时按 v0.9 的方式核对 manifest、题目注册、4B 快照和 adapter 哈希。
- 对照臂：v0.9 正式 run `a21767fe…` 的 RL_seed42/43/44，在 v0.9 登记的里程碑（第 200 步）。冻结时核对 v0.9 的 manifest、里程碑记录和 adapter 哈希，同一晚重新评测。
- 训练：与 v0.9 的 RL 逐项相同，冻结时与 v0.9 的设置逐项核对。
  - RLOO；每步 16 题 × 8 条，温度 1.0，不截断（top_p=1）；
  - lr 2e-5，前 5 次更新线性预热；梯度范数裁剪 1.0；
  - 截断重要性权重 min(π_θ/π_vLLM, 2)；不加 KL，不加熵奖励；
  - LoRA r16 接着 PTR 训练；损失分母为常数 16 × 8 × 512；
  - 每 10 步一个里程碑，每 20 步在 dev 上贪心评一次只作曲线；
  - 一个 run 占一张卡，vLLM 与训练进程同卡，每步更新后重新读入 LoRA。

## 唯一改动：训练题

- **预采样**：每个 seed 用自己的 PTR 起点（vLLM 带该 LoRA）把 pool 的 6682 题每题采 8 次，由 train-only oracle 判对错。采样参数与训练完全相同：温度 1.0、top_p=1、同一协议和预算。
- **边界题**：8 次里做对 1–7 次的题。金标执行失败、oracle 无法判分的题剔除；因上下文超长被拒的对话按错计，与训练一致。
- **取题**：每个 seed 只在自己的边界题上训练。排序规则与 v0.9 的 `task_order` 相同，只是作用在边界题上（按 `sha256(salt:online:seed:task_id)` 排序）。每步顺序取 16 题，取完从头循环。
- **门禁**：任一 seed 的边界题占可判分题的比例不在 5%–60% 之间，就停机检查、不训练。这条用来防预采样本身出错，只看训练题池，不看任何评测分数。
- **预估**：按 v0.9 的信号比例，每个 seed 约 900–1300 道边界题，200 步共取 3200 次，约过 2.5–3.5 遍。

## 步数与比较点

- **预注册比较点 K**：三个 RLb run 都达到的最大里程碑，上限 200，与 v0.9 的 K 相同。沿用 v0.9 的规则：某个 run 的最后里程碑不到最好那个的一半时记为“过短”，不拉低 K，只在它自己的最后里程碑上评测并单独标注。
- **探索性续跑**：K 的评测做完之后，三个 run 从第 200 步的检查点接着训到第 400 步，在第 400 步评测。只作描述，不参与判定。

## 评测

- 贪心，dev / validation / test，同一晚。条件：B、PTR×3、RL9×3、RLb×3（在 K）；探索性 RLb×3（在第 400 步）。
- 主指标为项目判分，官方 EX 并列。区间为数据库×seed bootstrap 95%，按 seed 配对。

## 预注册比较与判定

- **主比较 RLb−PTR**（项目判分）：test 均值 > 0、test 95% 下界 > 0，且 validation 均值 > 0，判为成立。标准与 v0.9 相同。
- **次比较 RLb−RL9**：同一标准。
- 探索性，不参与判定：
  - RL9−PTR：同晚重评 v0.9 的主比较，不改变 v0.9 的判定；
  - RLb@400−PTR、RLb@400−RLb；各家族 −B；官方 EX；
  - 预采样：每题做对几次的分布、边界题数、可判分题数；
  - 训练过程：奖励、有信号组占比、遍数、熵、轮数、生成长度、训推 log 概率差、TIS 截断比例；
  - 三种退化行为（首个输出解析失败、不查数据就提交、连续两次查询同一条 SQL）在训练中每 20 步的占比和评测时的占比；
  - dev 曲线、错误类型。
- 不选最终家族（v0.9 已选 RL），不看 validation 或 test 挑步数。

## 上机：单张 H20，一次约 3 天预约

- 同一张卡上依次运行：
  1. 冒烟：每个角色 16 题；预采样每题 4 次，RLb 训 2 步暂停后续到 3 步，并跑各类评测。
  2. 评测 B 和 PTR。
  3. 三个预采样。
  4. 三个 RLb 训到 K。
  5. 评测 RLb@K 和 RL9，出预注册报告。
  6. 探索续跑到第 400 步，评测后补充报告。
- 预约不够长时，调度器先保预注册部分：训练按截止时间给评测和报告留出时间，探索部分排在最后。
- 预估：预注册结论约在开机后 20–23 小时出来，全部约 31–34 小时。

## 附带：给 v0.10 的 4% 定案（不属于本研究）

- 背景：v0.10 的版式基准里，同一批轨迹在参数更新前的第一步梯度范数，4 卡是 0.0956，8 卡是 0.0919。fp32 下 1/2/4/8 卡的梯度一致（`tests/test_v10.py`），剩下的问题是 4B 在 bf16 下对微批组成有多敏感。
- 做法：
  1. 用 v0.10 的代码新冻一个只用来合并的 run，合并 PTR_seed42；
  2. 用 `bench --regroup` 在这张卡上，按 4、8（以及 2、16）卡的分法回放 v0.10 第一步的轨迹；
  3. 与 `bench/z3-4.json`、`z3-8.json` 的 first_grad_norms 对照。
- 判读：
  - 单卡回放出 0.0956 和 0.0919：差异来自 bf16 下的微批组成，8 卡的速度数字可以用；
  - 两种分法在单卡上一致：差异出在多卡路径上，留到多卡时再查。
- 它只读 v0.10 的最终包，排在预注册报告之后，失败不影响 v0.11。

## 不声称的内容

- 不声称一定提升：单张卡、LoRA、200 步，结果好坏都如实报告。
- RLb−RL9 只说明本设置下“只训边界题”的作用，不推广到其他选题方式或规模。
- 边界题来自起点模型自己在训练题池上的采样，所以每个 seed 的训练题集合不同。这是方法的一部分，不是泄漏：只用训练题池和训练金标。
- 执行结果一致只说明在固定数据库快照上结果相同，不等于语义等价。单一数据集（BIRD），结论只适用于本协议。
