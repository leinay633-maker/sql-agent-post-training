# v0.8 预注册：先过门槛的 235B 老师蒸馏，对照带金标提示的自我纠正（4B）

写于 2026-10-12（北京时间），在任何 v0.8 运行之前。协议 `efa-v8-gated-teacher-v1`。

## 为什么有 v0.8

v0.7 的主假设没有成立，原因不在方法，而在老师：Qwen3-32B（2025 年 4 月的混合思考模型，非思考模式）在本协议下并不比学生 Qwen3-4B-Instruct-2507 强（test 官方 EX 49.2% 对 48.9%，validation 50.9% 对 58.3%；pool 上各自做对约 3436 题，重合 2754 题）。上机前没有实测老师，是设计失误。同时 v0.7 留下两条仍然成立的线索：老师轨迹补到 4B 全错的题上（TR）在 test 上 +1.6 [+0.2, +3.0]（项目判分）；执行验证本身值约 10 个点（T−T_raw）。

v0.8 只改老师这一处，并把“老师先证明自己更强”写成门槛：

1. **主问题**：一个在 dev 上明显强于 4B 的老师，它经执行验证的轨迹补到 4B 全错的题上，能否让 4B 比只用自己轨迹（R）学得更好（TR vs R）。
2. **对照与备用**：不用任何外部老师，让 4B 自己在这些题上带着金标 SQL 作提示重做，验证通过后去掉提示再训练（HR，STaR 的 rationalization 思路）。它回答“大老师到底比金标提示多给了什么”（TR vs HR）；老师过不了门槛时，它是本晚的主结果。

## 固定内容

- 题目：沿用 v0.5 注册（pool 6682 / dev 615 / validation 1612 / test 1501；test 为 BIRD 官方 dev 去掉参考 SQL 预检排除的 33 题），新机器上重新校验题目文件与数据库哈希。**新数据只在 v0.5 第一轮 4B 全错的 3247 道 pool 题上生成**（第一轮每题约 2 条全部做错）。
- 模型（固定 revision，逐文件 SHA-256；ModelScope 与 HuggingFace 文件字节相同，已逐个核对）：
  - 学生：`Qwen/Qwen3-4B-Instruct-2507` @ `cdbee75f17c01a7cc42f958dc650907174af0554`（与 v0.5 同一快照，指纹 `45ba5b8b…`）
  - 老师：`Qwen/Qwen3-235B-A22B-Instruct-2507-FP8` @ `e156cb4efae43fbee1a1ab073f946a1377e6b969`（官方发布的 128×128 块 FP8 权重，约 236 GB；4 卡张量并行）
  - 两者 `tokenizer.json`、`tokenizer_config.json`（含对话模板）、`vocab.json` 逐字节相同（`merges.txt` 只差一行 `#version` 头），都是只有非思考模式的 2507 指令版，老师对话可直接按学生模板训练，不需要 v0.7 的自定义模板。
- 为什么选这个老师：它与学生同一代、同一套后训练流程，是该代最大的指令模型；官方模型卡上它在工具调用和 Agent 测评上明显高于 4B-2507（BFCL-v3 70.9 对 61.9，TAU2-Retail 74.6 对 40.4，LiveCodeBench v6 51.8 对 35.1）。这只是选候选的理由，**能不能用由下面的门槛实测决定**。
- 门槛（预注册，dev 是唯一选择集）：老师与 4B 各在 dev 615 题上贪心评测一次（同一 Agent 协议、同一判分），B235−B（项目判分）≥ **+5.0 个点**，且数据库 bootstrap 95% 下界 > 0，才生成 TR。未过门槛、老师加载失败或评测失败，都不生成 TR/PTR，如实报告。冒烟 run 不判门槛。
- Agent：v0.5 的无金标多轮状态机（最多 4 步，含一次结果复核），无列描述；上下文 8192，单步输出 512 token；接受裸 JSON 或恰好一个 ```json 代码块；停止符取 `generation_config` 的 eos。与 v0.7 相同。
- SQL 限制：10 亿 VM 步为主约束，墙钟 30 秒兜底，1 万行，8 MB。dev、validation、test 的参考结果在冻结时缓存。
- 采样：vLLM；两个模型的模型卡都推荐 T=0.7、top_p=0.8、top_k=20，采样都用这一设置。老师每道全错题 **K=4** 条（窗口 75 分钟），提示版 4B 每题 **K=2** 条（窗口 40 分钟）；同一题的 K 条连续调度；64 片认领；未采满按实际覆盖报告。
- HR 的提示：采样时在用户消息的公开 JSON 末尾追加 `reference_sql`（该题金标 SQL）和一句说明（“已知它返回正确结果；照常做题，先用查询看数据，再提交返回相同结果的 SQL”。4B 平时每题都先查询，说明保留这个习惯；v0.7 的 T 学到了老师约三分之一题不查询的习惯）。选中的轨迹在分词前删掉这两个字段，得到的用户消息与不带提示时逐字节相同（有测试）；助手轮次只能是 JSON 动作，没有自由文本。金标只用于 train 的 pool 题（与 RFT 的执行验证同一来源），评测时任何模型都看不到。
- 数据：TR 与 HR 都是 v0.5 的 R 全部 3435 例，加上每道全错题按 v0.5 规则选一条经执行验证正确的轨迹（前沿题优先，错误轮与被纠正的错误提交不监督，超长跳过），新增上限 4096 例。两份数据的新增例数会不同，TR−HR 的比较因此混有数据量差异，报告时并列给出例数。
- 训练：与 v0.5 R 完全相同（LoRA r16/α32/dropout 0.05/all-linear，lr 2e-4，warmup 3%，线性衰减，每步 16 例，1 epoch，最长 8192 token，seed 42/43/44），单次时间上限 2.5 小时。第二阶段与 v0.5 P 完全相同（v0.5 的 547 对偏好数据，β=0.1，lr 2e-5，SFT 权重 1），分别接在 TR 和 HR 上（PTR、PHR），不再先在 dev 上二选一。
- 评测：贪心，dev / validation / test 全部条件：B、R×3、P×3（v0.5 导入，同晚重评）、TR×3、HR×3、PTR×3、PHR×3；老师 B235 在 dev（门槛）以及 validation / test（只作报告，最低优先级）。主指标项目判分，官方 EX 并列；区间为数据库×seed bootstrap 95%。

## 预注册比较与判定

- **主比较 TR−R**（test，项目判分）：test 均值 > 0 且 95% 下界 > 0，且 validation 均值 > 0，判为成立。与 v0.7 同一标准。
- **次比较 HR−R**：同一标准。
- 探索性：TR−HR，PTR−P，PHR−P，PTR−TR，PHR−HR，各家族−B，B235−B（validation/test）。
- 最终家族：R、P、TR、HR、PTR、PHR 中，dev 三 seed 均值最高且三个 seed 在 dev 上都完整的那个；validation 与 test 不参与任何选择。
- 窗口：2026-10-12 20:00 至 10-13 02:00 的 8×H20（到点回收），计算截止 01:35。排不进窗口的作业不启动，写进 STATUS；缺的条件如实报告缺失，不补跑、不外推。

## 工程变化（不影响上面的协议）

- vLLM 0.11.2 的 MoE 算子库 `_moe_C` 在 glibc 2.28 上加载不了。逐个检查 wheel 里的 .so：只有它要 2.14 以上的 glibc，而且只为 `log2@GLIBC_2.29` 一个符号。`scripts/patch_moe_glibc.py` 把这条版本需求改指 `GLIBC_2.2.5`（glibc 2.28 仍导出该版本的 `log2`，同一函数），只改 5 个字节，别的符号绑定到该版本就拒绝修改。上机后先验证算子能导入；导入失败时老师路径自然失败，HR 照常。
- 调度器：作业可以占多张整卡（老师 4 卡张量并行）；等待中的多卡作业会占住一组卡，小作业不再往里填；老师还有活时（下载、门槛、采样），长时间的学生作业不进老师那组卡；时长估计用同类作业的实测值（v0.7 写死 3.2 小时导致空转约 3 小时）；排不进窗口的作业写一条说明。
- 下载：大文件按 1 GiB 分段并行（v0.7 实测单连接 5–10 MB/s），老师在主环境装好前就开始下载。
- 冒烟：每个角色 16 题，跑通采样（老师与提示版 4B）、选样、训练、P、评测、门槛与报告；正式 run 的每条路径等冒烟跑通同一路径才开始。
