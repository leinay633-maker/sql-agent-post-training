# v0.12 预注册：同一个 235B 老师，在线蒸馏（OPD）对照离线蒸馏（TR），都从原版 4B 出发

写于 2026-10-22（北京时间），在任何 v0.12 运行之前。协议 `efa-v12-opd-v1`。

## 为什么有 v0.12

- v0.8 用 235B 老师做的是离线蒸馏：老师在 4B 全错的题上采样，经执行验证留下做对的 832 条，和 4B 自己做对的 3435 条一起 SFT，得到 TR。主比较 TR−R 成立：test +2.4 [+0.8, +4.3]（项目判分）。
- v0.9 的在线 RL 用执行结果作奖励，一条对话只有一个 0/1。每步 16 题 × 8 条里，有训练信号的组只占 12.7–20.2%。主比较 RL−PTR 没有成立：test +1.4 [−0.1, +2.8]。
- 在线蒸馏（on-policy distillation，OPD）把两者接起来：学生自己采样（在线），老师对学生采出的每个 token 给出 log 概率，作为逐 token 的信号。梯度里不用金标。
- v0.8 的老师在 test 上没有评测（调度器估计排不进截止）。这次老师本来就要加载，顺带补评。

问题：

1. **主问题**：同一个老师、同一个起点（原版 4B），在线逐 token 蒸馏能否超过离线蒸馏 TR（OPD vs TR）。
2. **次问题**：在本协议下，OPD 从原版 4B 出发能否带来提升（OPD vs B）。
3. **附带**：老师在 test 上的分数，只作报告。

事先估计（写在任何运行之前）：v0.8 当晚，老师只比 TR 高 1.4–1.9 个点（dev 62.1% 对 60.7%，validation 60.0% 对 58.1%）。OPD 大体是把学生拉向老师，所以主比较的空间很小，“分不开”是很可能的结果。结果如何都照实报告。

## OPD 训练（唯一的新方法）

- 起点：原版 4B 加一个新初始化的 LoRA，结构与 R、TR 相同（r16/α32，all-linear），初始化用 seed。LoRA 的 B 矩阵初始为零，所以第 0 步的策略就是原版 4B。训练时关闭 dropout（采样没有 dropout，沿用 v0.9）。
- 采样：每步按 seed 固定打乱的 pool 顺序（v0.9 的 `task_order`，同一 salt）取 32 题，每题 4 条对话，共 128 条，与 v0.9 每步的对话数相同；取完从头循环。温度 1.0，top_p=1，不设 top_k。vLLM 与训练进程同卡，每步更新后重新读入 LoRA（沿用 v0.9）。
  - 为什么是 32 × 4，而不是 v0.9 的 16 × 8：OPD 的信号逐 token 来自老师，不需要组内基线。同样 128 条对话，可以多覆盖一倍的题。每题 4 条与 Thinking Machines 公开的 OPD 默认设置相同（每批 64 题 × 4 条）。
- 老师打分：
  - 每条对话取最后一轮的完整 token 序列。它已经包含之前各轮按对话模板重新渲染后的 token，v0.9 核对过这种对齐。
  - 把 token id 原样送给老师，老师返回每个位置上实际 token 的 log 概率（原始 logits，温度 1，不截断）。
  - 只用学生采样出的助手 token（含结束符）；系统、题目、工具返回只作条件。
  - 老师看到的上下文与学生完全相同，不含金标和对错。
- 逐 token 信号：A_t = log π_老师(y_t) − log π_vLLM(y_t)，不回传梯度。它是逐 token 反向 KL 单样本估计的相反数。只取当前 token 这一项（折扣为 0），与 Thinking Machines 的 OPD 做法相同。
- 损失：−Σ_i Σ_t w_t · A_t · log π_θ(y_t) ÷（32 × 4 × 512），其中 w_t = min(π_θ(y_t) / π_vLLM(y_t), 2)。除了 A 从整条对话一个值变成逐 token 一个值，其余与 v0.9 相同：常数分母，截断重要性权重。
- 不进梯度、单独计数的对话：
  - 重新分词后与采样 token 对不上（v0.9 的规则）；
  - 老师返回的 token 与送去的不一致，或 log 概率缺失、不是有限值。
- 被上下文拒绝的对话，已采样的轮次照常打分和训练，因为 OPD 不需要最终答案。金标无法判分的题也照常训练。
- 金标只用于记录：训练题上的执行对错照 v0.9 记成“训练奖励”，只作描述，不进梯度。
- 优化：AdamW（无权重衰减），学习率 1e-4，前 5 次更新线性预热，之后不变；梯度范数裁剪 1.0；不加 KL 正则，不加熵奖励。
  - 为什么是 1e-4：这次没有时间扫学习率。Tinker cookbook 的蒸馏配方里，LoRA 下的 OPD 用 1e-4（https://tinker-docs.thinkingmachines.ai/cookbook/recipes/distillation/）。v0.9 的 2e-5 是接着一个训好的 LoRA 继续训，这里是从零开始的 LoRA。
- 里程碑：每 10 步存一个 adapter；每 20 步在 dev 上贪心评一次，只画曲线（沿用 v0.9，在学生自己的卡上评）。
- LoRA 检查：新 LoRA 在第 0 步没有作用，v0.9 在第 0 步做的检查必然是 inconclusive。所以改在第 10 步采样后、更新前做，规则与 v0.9 相同：vLLM 的采样 log 概率与“基座 + 当前 LoRA”的平均绝对差，必须小于它与“光基座”的差，而且小于 0.15 nat/token。
- 步数：上限 400。训练在计算截止前 45 分钟停（与 v0.9 相同），不暂停、不续跑。
- **比较点 K**：三个 OPD run 都到达的最大里程碑。沿用 v0.9 的规则：某个 run 的最后里程碑不到最好那个的一半时，记为“过短”，不拉低 K，只在它自己的最后里程碑上评测并单独标注。不看任何评测分数挑步数。

## 探索臂：从 TR 接着做 OPD（2026-10-22 补，在任何 v0.12 运行之前）

- 用户问到“SFT 冷启动 + OPD”。在本项目里 TR 本身就是 SFT（4B 自己的轨迹加老师补的轨迹），所以冷启动版本就是从 TR 接着做 OPD，不另训冷启动模型。记作 TROPD。
- 只做 seed 42：起点是导入的 TR_seed42 adapter，接着训练这个 LoRA。其余与主臂 OPD 完全相同（取题顺序、每步 32 题 × 4 条、逐 token 信号、损失、学习率、第 10 步的 LoRA 检查、步数上限和训练截止）。
- 占第 8 张卡（7 号）。老师打分时它是低优先级：三个主臂有请求在排队时它等着；它的请求切成每段 32 条，主臂的请求最多多等其中一段。所以它的步数可能比主臂少很多，照实报告。它等老师不设时限，等到它自己的训练截止为止，排不上的时间不算失败。
- 评测点：min(K, 它自己的最后里程碑)，沿用 v0.9 对 RLhi 的规则，报告时注明步数。
- 只作探索，不参与任何判定：TROPD−TR、TROPD−B，以及与同 seed 的 OPD_seed42 对照。一个 seed，不计算统计结论。
- 对照评测（B、TR、PTR）原计划放在 7 号卡上训练期间跑，现在改为正式训练开始前在 5–7 号卡上跑完，没跑完的在 7 号卡上接着跑，跑完再开 TROPD。

## 预注册比较与判定

- **主比较 OPD−TR**（项目判分）：test 均值 > 0、test 95% 下界 > 0，且 validation 均值 > 0，判为成立。标准与 v0.7–v0.11 相同。
- **次比较 OPD−B**：同一标准。
- 某个 seed 的 OPD 一个里程碑都没有，或者评测失败：按实有的 seed 计算并注明。三个都没有：两项都记未判定，不补跑。
- 探索性，不参与判定：
  - OPD−PTR；各家族 −B；官方 EX；
  - OPD−R 和 OPD−老师：R 的分数和老师的 validation 分数取自 v0.8 当晚，注明隔晚；
  - 训练过程：逐 token 反向 KL 估计（采样 token 上 log π_vLLM − log π_老师 的均值）、训练奖励、熵、轮数、生成长度、训推 log 概率差、TIS 截断比例、老师打分耗时；
  - v0.10 诊断的三种行为（首个输出解析失败、不查数据就提交、连续两次查询同一条 SQL）在训练中每 20 步的占比和评测时的占比。其中“不查数据就提交”另与老师自己评测时的比例对照：v0.7 的 T 学到过老师少查询的习惯；
  - dev 曲线、错误类型。

## 上机先排风险

- 本机 CPU 测试，用随机初始化的小 Qwen3、脚本化引擎和假老师，都不是模型结果：
  - 老师与学生是同一个模型时，逐 token 信号全为 0；
  - 学生与老师不同时，按 OPD 训几步，两者在采样 token 上的反向 KL 估计下降；
  - 把信号的符号改反，上一条测试必须失败（反证）；
  - 多轮对话里，老师 log 概率与学生 token 的位置对齐：助手 token、结束符、工具返回、被截断的轮次、被上下文拒绝的对话；
  - 老师返回缺失或非有限值时，对话不进梯度并计数；
  - 训练截止、里程碑和 K 的规则；断点恢复；调度器按卡分工的全流程。
- 上机门禁：
  - 学生：同 v0.9，vLLM 挂 LoRA 实际采样并返回 log 概率。
  - 老师打分自洽对账：老师在 train 题上自己生成 32 段（温度 1，top_p=1，记下生成时的 log 概率），再走打分路径重算这些 token。返回的 token 必须与送去的完全一致、全是有限值，平均绝对差小于 0.15 nat/token（与 v0.9 的 LoRA 检查同一阈值）。这条用来抓错位和模板错，数值噪声远小于这个阈值。实际的均值和最大值记进 STATUS。
  - vLLM 0.11.2 的 prompt logprobs 在 4 卡张量并行下，项目里从没用过。显存和速度都以门禁和冒烟的实测为准。
- 冒烟时记录老师打分的显存峰值和每批耗时，正式部分的步数估计用这个实测值。
- 正式 run 开始后每 30 分钟导出一次结果包（沿用 v0.9）。

## 不声称的内容

- 不声称 OPD 一定提升：一晚、LoRA、最多 400 步、3 个 seed，结果好坏都如实报告。
- TR 用了金标筛选（4B 自己的轨迹和老师的轨迹都经执行验证），OPD 的梯度里没有金标。所以主比较回答的是：同一个老师下，不用金标的在线逐 token 蒸馏，对照用金标筛选的离线蒸馏。它不是纯老师数据 SFT 与 OPD 的对照，因为 235B 老师没有纯老师数据的 SFT 臂。
- 两种方法的计算量和见过的题不同，比较的是它们各自在本协议预算下的结果。
- 老师的 test 分数是隔晚补评，与 v0.8 当晚的 dev、validation 分数不是同一晚。
- 执行结果一致只说明在固定数据库快照上结果相同，不等于语义等价。单一数据集（BIRD），结论只适用于本协议。
