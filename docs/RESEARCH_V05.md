# v0.5：执行验证的多轮拒绝采样微调（RFT）

状态：2026-10-10 预注册的方法与工程实现，计划在 2026-10-11 17:00–10-12 01:00 的 8×H20 上执行。本文件在看到任何 v0.5 结果之前写定；改动协议要换版本，不能按验证或测试分数回头改。

## 1. 为什么换方法：v0.3.1 的诊断

v0.3.1（`h20-20261009-6gpu-v031`）在 256 道验证题上：B（基座+执行反馈）55.1%，C（成功轨迹 SFT）55.1–55.5%，D（规则修复 SFT）35.9–38.7%，主比较 D−C 三个 seed 均为 −17 到 −20 个百分点。逐题行为：

| 条件 | 用过 query 的题 | 中途报错的题 | 其中最终修好 | 同一 SQL 原样重复提交 |
|---|---|---|---|---|
| B 基座 | 256/256 | 36 | 17 | 2 |
| C seed42 | 0 | 21 | 4 | 234（含复核轮确认） |
| D seed42 | 0 | 60 | 0 | 254 |

结论：v0.3 只监督最后一个 finish，训练把基座“先查再交、报错后修”的工具行为抹掉了；D 的报错上下文 97% 来自规则扰动（512 对中自然修复 17 对），目标 SQL 与上下文里的错误 SQL 只差一个 token，模型学成“照抄上一条 SQL”。这一诊断看了验证集上的行为分布，但没有在验证集上选择超参数；下文所有数值在跑之前固定。

## 2. 研究问题与预注册比较

问题：用训练集 gold 的执行结果筛选模型自己采样的多轮工具轨迹（含真实执行报错后的修复），对整条轨迹的有效助手动作做监督，能否在相同推理协议下提高 4B Agent 的执行正确率？

| 代号 | 含义 |
|---|---|
| B | Qwen3-4B-Instruct-2507 基座，同一评测协议，不训练 |
| R | RFT：全部正确轨迹可选（含自然修复），报错动作与被纠正的错误提交不计损失 |
| R_clean | 消融：只允许“无报错、无改交”的干净正确轨迹，其余规则与 R 相同 |
| P | 第二阶段：每个 seed 从自己的 R 继续，用同题“做对 / 做错”轨迹对做偏好优化（第 8 节） |

- **主比较**：R − B，验证集全量 1612 题（14 库），三个训练 seed 42/43/44 合并，报告均值差与“数据库 × seed”配对 bootstrap 95% 区间（`rl.reporting.paired_report`），并列出每个 seed 的数据库聚类区间。
- **次要**：R − B 在 BIRD 官方 dev（最终独立测试）；P − B 与同 seed 的 P − R；R − R_clean（seed 42，探索性消融）；v0.3.1 那 256 题子集上的数值（与旧结果衔接）。
- 最终模型在 R 和 P 之间只按 dev 上三 seed 的平均正确率选，验证集和测试集两者都报。
- 三个 seed 都报，不挑最好的；失败、超时、协议错误、未完成都留在分母。

## 3. 数据划分

全部沿用 v0.3.1 study 的 prepared 划分和参考 SQL 预检排除名单（prepare 阶段按其 `study.json` 记录的哈希核验）：

| 用途 | 来源 | 题数 |
|---|---|---|
| 采样训练池 | train 划分去掉排除题和 dev 库 | 6682（49 库） |
| dev | train 划分里按 `sha256("20261010:"+db)` 排序取前 6 个库：genes、world_development_indicators、beer_factory、app_store、olympics、cars | 615 |
| 验证（主比较） | validation 划分全部未排除题 | 1612（14 库） |
| 最终测试 | BIRD 官方 dev.json，用同一 SQL 限制做参考 SQL 预检，排除项单列 | 约 1534（11 库） |

dev 只用于本机 pilot、工程门禁和第二轮是否采用的判断，从不进训练；验证集和 BIRD dev 不进采样、筛选、选超参。BIRD dev 在所有模型冻结后只评一次。

## 4. 采样

- 策略：基座 BF16，Transformers `generate`；`temperature=1.0, top_p=1.0, top_k=0`（不截断的原始分布），每步最多 512 输出 token，上下文 8192。
- 温度改动（2026-10-10 20:03，早于任何 v0.5 的 dev / 验证 / 测试结果）：原定模型卡推荐的 T=0.7、top_p 0.8、top_k 20。本机 NF4 pilot 在训练池上显示这组参数下采样几乎是确定性的：同一题 4 条样本平均只有 1.64 种不同的最终 SQL，300 题里只有 41 道边界题，pass@1/2/3/4 为 52%/57%/58%/58%（100 题子集）。同一批题上 T=1.0 的 56 条首轮样本：单条准确率 28/56，与 T=0.7 首轮相同；每轮输出约 46 token（T=0.7 为 45），没有截断；做对 2 道 T=0.7 四条全错的题，没有丢掉 T=0.7 四条全对的题。证据只有 56 题，T=1.0 能多发现多少边界题要以 H20 上的采样统计为准；本机 3080 显存与桌面共用，T=1.0 的 400 条没能采完。
- 交互协议与评测完全相同：最多 4 个助手步、执行反馈、首次成功提交的结果复核轮、同一 SQL 限制（10 s、10000 行、8 MB、10 亿 VM 步）。
- 每题最多 K=6 条，每片墙钟预算 45 分钟；顺序为“先给所有题采第 1 条，再第 2 条……”，题序用 `sha256("20261010:"+id)` 固定；8 张卡按序号取模分片。预算用完时不再开新对话、已开始的跑完，实际每题采样数写进报告。K 从最初写的 4 改为 6 是在任何 v0.5 结果之前（2026-10-10 11:58）做的：同样的时间预算下，吞吐够就多采、多发现边界题，不够就停在实际条数。
- 判分：只在 train 题上用 gold 重新执行最终 SQL 判对错；中途通过复核轮后又改交的 finish 也重新执行判对错，用于掩码。gold 不进入模型可见的任何消息。

## 5. 选样与掩码

- 可用轨迹：最终 `submitted` 且判对，没有生成截断。
- 题目分层：实际采到的条数中对了一部分的为“边界题”，全对为“简单题”。顺序为边界题（固定种子打乱）在前、简单题在后，取前 **4096** 道题，每题随机取 1 条可用轨迹（种子 20261010）。R_clean 用同一题序，只在干净轨迹里取，没有干净轨迹的题跳过并顺延补足 4096。
- 每条轨迹的所有助手动作默认计损失；以下动作的 token 标为 -100：观察结果为错误（SQL 错误、超时、协议错误、结果超限、只读拒绝等）的动作；执行成功但判错、随后被改交的 finish。问题、schema、工具结果只作上下文。
- 报告：每题采样数、通过率分布、边界/简单题数、修复轨迹占比、被掩码动作数、监督 token 数。

## 6. 训练

LoRA r=16、alpha=32、dropout 0.05、all-linear；学习率 2e-4，warmup 3%，线性衰减；有效 batch 16（micro 4 × 累积 4），1 个 epoch = 256 步；最长 8192 token，不截断，超长样本整题跳过并计数；梯度检查点开启；BF16。seed 42/43/44 只改变 LoRA 初始化和样本顺序，三份共用同一份选样。训练后保存 adapter 并做重载 logits 校验。

## 7. 评测

所有条件同一协议：贪心解码、最多 4 步、执行反馈、结果复核轮、同一 SQL 限制、generate batch 16（固定微批，同一题序）。SQL 执行在批内并行，只影响速度。B、R×3、R_clean×1 在 dev、验证全量、BIRD dev 三个集合上评测；每个评测目录冻结模型身份、题目列表和代码指纹，可续跑但不能换模型续跑。

## 8. 第二阶段：执行结果偏好优化（P）与时间安排

RFT 只用做对的轨迹。本机 pilot（NF4，300 道训练池题 × 4 条，T=0.7）显示采样结果高度两极：147 题 4 条全错、112 题全对，只有 41 道边界题，说明正确轨迹之外的失败信息没有被利用。第二阶段用这些失败轨迹（2026-10-10 17:50 决定，早于任何 v0.5 的 dev / 验证 / 测试结果）：

- 轨迹对：第一轮采样里同一道训练题，随机取 1 条做对的轨迹（掩码规则同第 5 节）和 1 条做错的轨迹（答错、最终 SQL 执行失败或步数用完；做错轨迹的全部助手动作都计入），每题 1 对。只来自训练池，dev、验证、测试不进入。
- 训练：每个 seed 从自己的 R adapter 继续；同一 adapter 在任何更新前的输出概率作为参考。损失 = DPO（β=0.1）+ 做对轨迹的 token 平均 NLL（权重 1，RPO 写法，防止正确轨迹概率随 margin 一起下降）；学习率 2e-5，warmup 10% 后线性衰减，每步 16 对，1 个 epoch，关闭 dropout，梯度裁剪 1.0。
- 时间表（8 小时窗口，计算截止 00:00）：启动 → 采样约 45 分钟 → 选样与构建配对（CPU）→ R×3、R_clean×1 训练，同时评 B → P×3 训练与 R 的评测共用 8 张卡 → 评 P → 报告。
- 若 P 全部评完后离截止仍有 2 小时以上，再做第二轮 RFT（用 R seed42 的 adapter 按第 4–5 节重新采样、选样，从基座训练 R2 三个 seed），R2 只作探索性结果报告，不参与最终模型选择。

## 9. 本机 pilot

RTX 3080 10 GB 装不下 4B BF16 训练，本机 pilot 用 NF4 量化的同一 4B 基座，在训练池子集上采样、训练，只在 dev 上比较 B 与 R。它只用来检查代码、产出比例和方向，不作为结果、不写进报告结论。

## 10. 限制

执行匹配是本项目的判分（多重集合比较，行数和列数必须一致），比 BIRD 官方 EX 严格，不是官方榜单分数。RFT 只学模型自己能做对的题，对完全不会的题没有直接信号；简单题占比、选样上限和学习率都是预先给定而非调优的值。验证集分布在 14 个库上，数据库间差异会让区间偏宽。
