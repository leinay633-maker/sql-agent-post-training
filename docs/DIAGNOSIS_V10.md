# v0.10 诊断：全参在线 RL 落后于 LoRA RL 时发生了什么

数据：v0.10 最终结果包 `v10-results-1021-0710-final.tgz`（59259801 字节，sha256 `151f6ed1…c6c1f96b`，run 7488b089f842）与 v0.9 最终结果包 `v09-results-1019-1717-final.tgz`（57837031 字节，sha256 `7e3b586d…ce08d5852`，run a21767fe09fa）。只用本机已有的轨迹、指标和评测记录，没有新的模型运行。下文的表由下面的命令生成，完整输出附在文末：

```bash
python -I scripts/v10_diagnose.py --run <v10 最终包>/outputs/v10/run --v09-run <v09 最终包>/outputs/v09/run
```

这是事后描述，不是预注册的判定，也不做因果归因。

## 1. 预注册结果（摘自 v0.10 报告）

- 主比较 RLF − RL：反向成立。test −4.2 [−7.1, −1.2]，validation −6.1 [−9.1, −2.9]（项目判分，数据库×seed bootstrap 95%，3 个 seed）。
- 次比较 RLF − PTR：不成立。test −2.6 [−5.4, +0.2]，validation −4.3 [−7.9, −0.5]。
- 报告里的 RL − PTR（test +1.6 [+0.2, +3.1]）是把 v0.9 的同一批模型合并成全参后重评一次，不是新证据。v0.9 预注册的这一比较 test 下界是 −0.1，判定不成立；同样的模型换一条推理路径重评，下界就从 −0.1 变成 +0.2，说明差距本身在误差边缘。它在 v0.10 里只作探索，不改 v0.9 的判定。对外的说法是“平均提升约 1.5 个点，预注册检验没有过线”。

## 2. 什么时候开始落后

同一个 seed 下，v0.9 的 RL 和 v0.10 的 RLF、RLFa 每一步抽到的题完全相同（三个 seed 都是 200/200 步），所以训练奖励可以逐步配对比较，不受抽题顺序影响。

- 前 60 步三者分不开：每 20 步一段，RLF − RL 在 −2.4 到 +1.4 之间。
- 之后 RLF 逐段落后，落后的时间各 seed 不同：seed 42 从第 61 步起（−3.6、−4.5），seed 43 在第 61–80 步和最后 40 步（−4.8；−5.0、−7.0），seed 44 从第 121 步起（−6.2、−9.3、−6.8、−6.5）。
- RLFa 的 seed 42 从第 121 步起落后 3.8–7.3 个点，seed 43 从第 81 步起落后 3.6–9.5 个点；seed 44 一直和 RL 相差 2.5 个点以内。

## 3. 落后的同时：每个 run 出现一种退化行为

LoRA RL 三个 seed 都没有出现下面任何一种：训练中每段各项占比都在 1.5% 以内，评测时和 PTR 相当（重复查询 1–3%，另两项不超过 0.1%）。全参的 6 个 run 里有 5 个各自出现其中一种，出现的时间和种类随 seed 不同：

| run | 退化行为 | 训练中出现 | 评测时（test） |
|---|---|---|---|
| RLF_seed42 | 连续重复同一条查询 | 第 121–180 步，最高占 44% 的轨迹；最后 20 步消失 | 0%，但改坏的题仍比修好的多 |
| RLF_seed43 | 连续重复同一条查询，输出变长（约 110 → 200 token） | 第 61 步起 31%，第 141–160 步最高 76%，最后 20 步 62% | 52% 的对话有相邻两次查询完全相同；94% 的对话动作序列是“查三次再提交”，其中三次 SQL 全同的占 30% |
| RLF_seed44 | 第一轮输出不是合法 JSON（SQL 字符串里多了一个双引号，字符串提前结束；test 上 428 次里 421 次是这种报错） | 第 141 步起，11% → 23% | 28.5% 的对话 |
| RLFa_seed42 | 不查数据，直接提交，再靠提交后的复核改 | 第 61–80 步 19%，第 81–100 步 93%，之后 100% | 100% 的对话 |
| RLFa_seed43 | 同上 | 第 141–160 步 61%，之后 100% | 100% 的对话 |
| RLFa_seed44 | 没有 | — | — |

validation 上的占比相同（RLF_seed43 重复 59%，RLF_seed44 不可解析 33%，RLFa_seed42/43 不查数据 100%）。“不查数据就提交”指第一次提交前没有查询；没有提交、整段都没查的对话也算在内。

训练奖励并不逐段跟着这些行为变化，所以这里只说它们和落后同时出现，不说是它们造成了落后：

- RLF_seed43 第 81–160 步重复查询占 42–76%，奖励差只有 −0.1 到 −1.6；明显落后的是第 61–80 步（−4.8）和最后 40 步（−5.0、−7.0）。
- RLF_seed44 第 121–140 步奖励已落后 6.2 个点，不可解析只有 1.0%（输出已到约 200 token）；不可解析升到 11–23% 是第 141 步以后。
- RLFa_seed42 第 101–120 步已经 100% 不查数据，奖励差只有 −0.2；拉开是第 121 步以后。
- RLFa_seed43 第 81–140 步落后 3.6–5.3 个点时还没有这个行为（0–0.1%），它从第 141 步才出现。

## 4. 评测上坏在哪里

- 最终 SQL 执行失败（test，三个 seed 合计）：PTR 16、RL 35、RLF 292、RLFa 207。RLF 的报错主要是 `no such column`（119）和 `ambiguous column name`（89），其次是一次提交多条语句（22）；RLFa 主要是 `no such column`（137）。RLFa 的 207 次执行失败里，seed 42、43 这两个不查数据就提交的 run 占 167 次（83、84），没有这个行为的 seed 44 是 40 次。
- 和同 seed 的 PTR 逐题比（test）：RL 修好 68–101 题、改坏 59–69 题；RLF 修好 122–149 题、改坏 143–199 题；RLFa_seed42/43 修好 110–111 题、改坏 189–226 题。全参改动的题比 LoRA 多得多，两个方向都多，改坏的更多。RLF_seed43 改坏的 199 题里有 68 题是执行失败。
- 报告的错误分析里，按难度看，RLF 比 PTR 掉得最多的是中等题（44.7% → 39.9%；难题 −2.8，简单题 −1.5）。按 SQL 特征看，除去只有 3 题的集合运算，含 ORDER BY/LIMIT 的题掉得最多（49.3% → 40.6%），含除法、CASE 的也掉了约 5 个点。

## 5. 能说和不能说

- 能说：在这个配方下（学习率 2e-6，不加 KL，200 步），全参在线 RL 的训练奖励从第 60 步以后陆续落后于同题的 LoRA RL（各 seed 开始的时间不同）；6 个全参 run 里有 5 个在第 61–141 步之间各自出现一种退化行为，评测时这些行为和执行失败、改坏的题同时出现（例外是 RLF_seed42：评测时已经不重复查询，改坏的题仍比修好的多，143 对 122）。LoRA RL 在同样的题、同样的步数下没有出现这些行为。训练奖励不逐段跟着行为变化，这些行为是不是落后的原因，这次的数据分不开。
- 不能说：“全参一定不如 LoRA”。RLF 和 RL 同时差了可训练参数（全部对 LoRA r16）和学习率（2e-6 对 2e-5），学习率只设了一个值（见 RESEARCH_V10.md 的“不声称的内容”）。退化是由全参本身、学习率还是缺少约束引起，这次的数据分不开。
- 如果做 v0.11，要单独预注册。可考虑的方向：对起点加 KL 约束、学习率降一档或扫两三个值、在线监控上表三种行为的占比。这些都会改协议，不能接着 v0.10 的结果算。
