# 部署研究：一张 H20 上部署训好的模型，合并和 FP8 各丢多少分、并发能扛多少

写于 2026-10-29（北京时间），在任何部署研究运行之前。协议 `efa-deploy-v1`。描述性研究，不做判定，不训练。

## 为什么做

- 之前的研究都停在离线评测：vLLM 离线引擎批量跑完整 test。还没有回答部署要问的几件事：
  - 把模型作为服务开出来，准确率和离线评测一样吗？
  - 合并 LoRA、量化成 FP8 各丢多少分？
  - 一张卡能扛多少并发？
- 本研究在一张 H20 上部署一个训好的模型，量这三件事，最后留一个可以录屏的演示。

## 固定内容

- 模型：v0.11 正式 run `7b9bca19…` 的 RLb_seed44，在 v0.11 登记的比较点第 200 步。
  - 选它的依据只看 dev：三个 RLb seed 在 dev 上分别答对 403、402、410 题（共 615 题），seed 44 最高。
  - 没有看 test 或 validation 选模型。
- 冻结时的核对：v0.11 的 manifest 身份、题目注册、4B 快照、里程碑记录和 adapter 哈希；里程碑必须正好在第 200 步、不是没训满的顶替；Agent 协议与 v0.11 逐项相同。
- 题目、Agent 协议、判分：与 v0.5–v0.12 相同。
  - test 1501 题、validation 1612 题；
  - 最多 4 步，含一次结果复核；上下文 8192，单步 512 token；
  - SQL 限制 10 亿 VM 步、墙钟 30 秒、1 万行、8 MB；
  - 项目判分，对照冻结时执行的金标缓存。
- 三种部署：
  - `lora`：原版 4B 加 LoRA，vLLM 挂 LoRA；
  - `merged`：沿用 v0.10 的合并（fp32 合并，在固定探针上核对与未合并模型的 logit 差不超过 1e-3，再一次取整到 bf16）；
  - `fp8`：`merged` 的权重由 vLLM 在加载时量化成 FP8（`quantization="fp8"`）。

## 测什么

1. **掉分**：
   - 三种部署在 test 和 validation 上各做一次贪心评测，评测路径与之前各版相同；三种部署用同一个题序，批次从相同的题开始；
   - 报告合并（merged−lora）、FP8（fp8−merged）和两者合计（fp8−lora）的差值；
   - 区间用数据库 bootstrap 95%（只有一个模型，不重采 seed）。
2. **压测**：
   - 服务路径：vLLM 的 OpenAI 兼容服务，前面是本项目的分析服务（`/api/analyze`，每个请求跑完整的 Agent 对话），一次只开一种部署，占整张卡。
   - 服务参数：`--generation-config vllm`，不用模型卡的默认采样；`--max-num-batched-tokens 16384`，与离线引擎在 70 GB 以上的卡上的默认值相同（服务端默认只有 8192）；停止符与评测路径相同（151643、151645），由分析服务随请求发送；贪心。
   - 题目：test 里按 `sha256(salt:bench:题号)` 取固定的 256 题。
   - 并发：1、4、16、64，按这个顺序各跑一遍这 256 题；每一档开始前，等 vLLM 显示没有在跑和排队的请求，再清空前缀缓存，使各档之间不复用 prompt。vLLM 的这个接口不确认是否清空成功，报告里照实写。
   - 预热：开始前先在固定题之外的 8 题上预热一次。
   - 每个请求记：客户端看到的延迟、结果、每次模型调用的 token 数、服务返回的编号；每完成一个就写盘。
   - 基础设施失败：没有 HTTP 200，或分析服务报告它的模型或数据库没有回答（`provider_error`、`schema_error`）。模型自己的结果（步数用完、输出不合格式）不算。预热一个都不允许；每一档最多 2%（256 题里 5 个），超过就不再发新请求，这种部署这次尝试作废、不写结果；冒烟 8 题一个都不允许。
   - 每次尝试一个目录，不覆盖之前的尝试；报告用写了结果的那次。
   - 每一档记：
     - P50 和 P95 延迟、每秒完成题数，只算正常答完的请求；另列全部请求的 P95；
     - vLLM 计数器算出的每秒生成 token 数和前缀缓存命中率；
     - 运行中采样的 KV 缓存峰值、在跑请求数和显存峰值；
     - 用项目判分事后给服务端的最终 SQL 打分，分母是全部请求。
3. **对齐**（在压测的 256 题上）：
   - 首轮 prompt 的 token 数：评测路径用聊天模板现算，服务端取 vLLM 返回的用量，应逐题相同；
   - 服务端最终 SQL 和对错，与评测路径比较：SQL 逐字比较，两边都没有最终 SQL 的单独计数、不算相同，服务端基础设施失败的题不参加比较；
   - 服务端并发 1 对并发 64 的差异作为数值噪声的基线：批次不同，浮点结果会有微小差别。
4. **演示**：研究跑完后另起，脚本是 `scripts/deploy_demo.sh`（上机手册未公开）。
   - 分析服务开在所有网卡上，vLLM 只在本机回环；两个服务都要密钥（vLLM 读 `VLLM_API_KEY`，分析服务读 `EFA_SERVER_KEY`，再用 `EFA_API_KEY` 带给 vLLM）；默认用合并模型，开 60 分钟；
   - 密钥只在这些环境变量和主机上的一个文件里：文件创建时就只有属主可读，不跟随软链；不进命令行和日志。
   - 演示期间占着研究的锁，研究和演示不会同时用卡；结束时自动把演示记录打进结果包。

## 分析服务的改动（旧行为不变）

- `service.max_concurrent`：同时运行的分析请求数，默认 1；大于 1 时必须用 HTTP 模型后端（进程内的模型不是线程安全的）。
- `service.review_success`、`service.fenced_json`：结果复核和接受 ```json 代码块，默认都关，与原服务一致。
- 每个请求返回自己每次模型调用的 token 数（`calls`）。
- `HTTPPolicy` 新增两项：
  - `complete()`：返回本次调用自己的用量，可以多线程同时调用；
  - `extra_body`：用来传 vLLM 的 `stop_token_ids`，不能覆盖固定字段。
- `agent.dialogue` 遇到有 `complete()` 的模型就逐次取用量；没有时仍按旧办法，从元数据的前后差算。

## 上机：单张 H20，约 6–7 小时，另加演示 1 小时

- 环境与冻结约 1 小时：validation 的数据库来自 BIRD train，所以 BIRD train 和 dev 都要下载（解压后约 50 GB）。
- 冒烟：每个角色 16 题、压测 8 题，并发 1 和 4，覆盖合并、三种评测、三种压测和报告。冒烟用 test、validation 的题，与 v0.9–v0.12 的冒烟相同：模型已经冻结，冒烟的数字只检查流程跑没跑通，不参与任何选择。
  - 冒烟里失败的步骤，正式 run 不再做同一步；
  - 合并失败时，`merged`、`fp8` 的评测和压测都不做。
- 正式：依次是合并（CPU，约 10 分钟）、6 个评测（约 1 小时）、3 个压测（约 2 小时，并发 1 那一档最慢）、报告。
- 预约不够时，按估时不再开始放不下的步骤，压测排在评测之后。
- 每一步每次尝试的时限是估时的两倍（至少 30 分钟），时限前 5 分钟不再开始新工作；每一步结束后，检查有没有被强杀的压测留下的服务进程，有就关掉，端口被占时压测不启动。

## 不声称的内容

- 单张卡、单个模型（RLb_seed44@200），结论只适用于这个模型和本协议。
- FP8 是 vLLM 加载时的在线量化，不代表离线校准过的 FP8 模型。
- 延迟包括 SQL 执行时间，是完整 Agent 对话的端到端延迟，不是单次生成的延迟。
- 压测的 256 题来自 test，只用来量速度和对齐，不用来选模型或调参。
